# Day 1 — 2026-07-14: Access Control Bypass Patterns

## Today's Research Focus

### Pattern: Missing Role Check in Withdrawal Functions

**Common vulnerability:** Contracts implement blacklist/role-based restrictions on `deposit()` and `stake()`, but forget to apply the same check to `withdraw()` and `unstake()`.

#### Example: Ethena StakedUSDeV2

```solidity
// VULNERABLE: unstake() has no FULL_RESTRICTED_STAKER_ROLE check
function unstake(uint256 _usdeAmount, address _to) external {
    // ... directly calls silo.withdraw()
}

// CORRECT: should add role check
function unstake(uint256 _usdeAmount, address _to) external {
    require(
        !hasRole(FULL_RESTRICTED_STAKER_ROLE, _msgSender()),
        "Blocked"
    );
    // ... rest of function
}
```

#### Key Takeaway
- Always audit ALL functions that move funds, not just the "obvious" entry points
- Check if blacklist/restriction roles are enforced consistently across ALL user-facing functions
- Look for secondary withdrawal paths (cooldown → silo → unstake) that might bypass primary checks

### Pattern: Incomplete State Cleanup After Penalty

```solidity
// VULNERABLE: burns shares but doesn't clear cooldown record
function redistributeLockedAmount(address from, address to) external onlyRole(BLACKLIST_MANAGER_ROLE) {
    uint256 sharesToBurn = balanceOf(from);
    _burnShares(from, sharesToBurn);
    // MISSING: delete cooldowns[from]; ← stale state allows later withdrawal
}
```

#### Key Takeaway
- When penalizing a user (burning shares, freezing funds), check ALL related state
- "Burning the token" is not the same as "clearing the debt" — if there's a pending withdrawal record, it can still be claimed
- Map all state variables that reference a user: balances, allowances, cooldowns, pending withdrawals
